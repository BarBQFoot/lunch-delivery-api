# แบ่งงานแบบ Greedy และเก็บเฉพาะ preview ปัจจุบัน

อัปเดต 27 ตุลาคม 2026 ใช้กับ backend `lunch-delivery-api` และ frontend `web-track-delivery` ทั้งหน้า owner และ test-api

## การสร้างแผน

1. ตรวจออเดอร์ 1–30 รายการและระยะร้านถึงลูกค้าแต่ละรายไม่เกิน 3 กม. ตามถนน
2. เริ่มใบงานจากออเดอร์หนึ่งรายการ
3. ลองออเดอร์ที่ใกล้จุดส่งสุดท้ายก่อน โดยใช้ตารางระยะทางตามถนน
4. ลองลำดับส่งของกลุ่มที่จะรวม สูงสุด 3 ออเดอร์ จึงมีไม่เกิน 6 ลำดับต่อกลุ่ม
5. รวมเมื่อส่งมอบทันกำหนด และค่าส่งรวมต่ำกว่าการแยกใบงานปัจจุบันกับออเดอร์ใหม่เป็นงานเดี่ยว
6. ถ้ารวมใครเพิ่มไม่ได้ จบใบงานนั้นแล้วจัดออเดอร์ที่เหลือต่อ ไม่ฝืนรวมให้ครบ 3

ไม่มี bitmask, Candidate ทุกกลุ่ม, search ย้อนกลับ หรือ bound แล้ว ยังใช้ `buildJob()` คำนวณระยะทาง เวลา ค่าส่ง และกำไร
Greedy ตัดสินใจทีละใบ จึงไม่รับประกันค่าส่งต่ำที่สุดทั้งแผน
เพดานออเดอร์ยังเป็น 30 ตามเดิม การเปลี่ยนนี้ไม่ได้เปิดรับแบบไม่จำกัด และไม่ได้ปรับความเร็วในการขอเส้น geometry จาก OSRM

## API preview

ครั้งแรกส่ง `POST /job-sheets/preview` ด้วย `order_ids` และ `settings` เหมือนเดิม
Frontend ผ่าน Angular proxy ใช้ `/api/job-sheets/preview`

เมื่อขอแผนอื่น:

```ts
{
  order_ids: [262, 263, 264],
  settings: currentPlan.settings,
  previous_preview_id: currentPlan.preview_id
}
```

- Backend อ่าน preview ปัจจุบันจากรหัสนี้ แล้วสลับลำดับออเดอร์เริ่มจัดด้วย Greedy
- เปรียบเทียบกลุ่ม order_id และลำดับส่งโดยตรง ไม่ใช้ hash และไม่ถือว่าการสลับตำแหน่งการ์ดเป็นแผนใหม่
- ลองไม่เกิน 10 ครั้งต่อคำขอ ถ้ายังไม่ต่าง ตอบ 422 และเก็บแผนเดิมไว้ การหาไม่พบในการลองครั้งนี้ไม่ได้ยืนยันว่าไม่มีทางเลือกอื่นทั้งหมด
- กดขอใหม่ได้เรื่อย ๆ และอาจวน A → B → A ได้ เพราะไม่จำประวัติ
- ถ้าแก้รายการออเดอร์หรือ settings สามารถส่งรหัสเดิมมาแทนที่ได้ แต่จะไม่บังคับให้รูปแบบเส้นทางต่างจากเดิม
- ไม่มี `signature` ใน response และไม่ใช้ `exclude_signatures` ใน request แล้ว ส่งชื่อฟิลด์เก่าจะได้ 400 เพื่อให้แก้ frontend ให้ตรงกัน

Response ยังคง `preview_id`, `expires_at`, `settings`, `jobs`, `summary`, `method` ให้การ์ด แมพ และ summary ใช้ต่อได้

## การเก็บและยืนยัน

- `rememberPreview()` ยังเก็บแผนปัจจุบันใน RAM เพื่อใช้ตอน confirm
- เมื่อได้แผนใหม่ จะสร้างรหัสใหม่ แล้วลบเฉพาะ preview ที่ระบุใน `previous_preview_id` หลังสำเร็จ
- ถ้าตรวจข้อมูล/OSRM/การจัดแผนไม่สำเร็จ จะไม่ลบ preview เดิม
- ถ้ามีคำขอแทนที่ซ้อนกัน คำขอที่มาทีหลังจะไม่สามารถแทนรหัสเก่าที่ถูกลบไปแล้วได้
- แผนของคำขออื่นไม่ได้ถูกล้างพร้อมกัน ยังมีข้อจำกัด cache รวม 50 แผนต่อโปรเซสและอายุ 30 นาทีเหมือนเดิม
- Backend restart, หมดอายุ, ยืนยันแล้ว หรือถูกแทนที่ จะใช้รหัสเดิมต่อไม่ได้ ตอบ 409
- `POST /job-sheets/confirm` ยังคงส่งเพียง `{ preview_id }` และตรวจออเดอร์ล่าสุดก่อนบันทึก transaction เหมือนเดิม
- ใบงานที่ยืนยันแล้วอยู่ในฐานข้อมูล ไม่ใช่ประวัติ preview และโหลดกลับมาแสดงได้ตามเดิม

## ฟังก์ชันหลักใน delivery-planning.ts

| ฟังก์ชัน | หน้าที่ |
|---|---|
| `buildJob()` | คำนวณใบงานจากลำดับที่รับมาและตัดลำดับที่ส่งไม่ทัน |
| `permutations()` | ลองลำดับภายในกลุ่มเล็ก ไม่เกิน 3 ออเดอร์ |
| `buildGreedyJobs()` | จัดงานทีละใบ รวมเฉพาะเมื่อคุ้มและส่งทัน |
| `shuffledIndexes()` | สลับลำดับเริ่มต้นเมื่อขอแผนอื่น |
| `sameDeliveryJobs()` | เทียบกลุ่มและลำดับส่งกับแผนปัจจุบันโดยไม่ทำ hash |
| `createDeliveryPlan()` | ตรวจข้อมูล เรียก Greedy และสรุปผลทุกใบงาน |

`return_to_shop` ยังอยู่ในโครงสร้างเดิม แต่ก่อนการปรับ Greedy โค้ดรวมทางกลับร้านใน `buildJob()` ถูกคอมเมนต์ไว้แล้ว รอบนี้ไม่ได้เปลี่ยนพฤติกรรมส่วนนั้น ต้องตกลงและแก้แยกหากจะเปิดตัวเลือกกลับร้านใช้งานจริง

## ตรวจรับ

- สร้างแผนแล้วออเดอร์ครบ ไม่ซ้ำ และไม่เกิน 3 ออเดอร์ต่อใบงาน
- ออเดอร์ห่างกันไม่ถูกฝืนรวมเมื่อแพงกว่าแยกส่ง หรือรวมแล้วส่งไม่ทัน
- เสนอแผนอื่นแล้วกลุ่มหรือลำดับส่งต่างจริง; หากหาไม่พบยังยืนยันแผนเดิมได้
- เปลี่ยนได้เกิน 20 ครั้ง และรหัสของแผนที่ถูกแทนที่ใช้ยืนยันไม่ได้
- แผนใหม่ยังโหลดเส้นผ่าน `/route` และยืนยันด้วย `/confirm` ได้
- ทดสอบด้วยข้อมูลจำลองก่อน ส่วนยืนยันลงฐานข้อมูลจริงให้ใช้ชุดข้อมูลทดสอบของทีม
